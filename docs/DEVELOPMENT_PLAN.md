# MealNote 开发计划

**目标：** 先跑通一餐记录的完整闭环，再逐步接入真实账号、AI provider 和中餐数据。  
**当前阶段：** 本地 demo 骨架。  
**工作方式：** 垂直切片、每步可运行、每个不确定性都保留回退。

## 1. 交付原则

1. 先验证“10 秒记录一餐”是否成立，再扩展平台功能；
2. 先建立 AI 输出和 Nutrition Engine 的边界，再接入具体模型；
3. 本地 demo 必须无凭据可运行，生产云接入必须显式配置；
4. 任何模型替换不能迁移或破坏用户历史、菜谱和营养快照；
5. 每个阶段都提供可手动完成的失败路径；
6. 保持单体结构，不为假设的规模提前引入微服务、Kubernetes 或向量库。

## 2. 当前基线与状态

当前仓库的文档和设计系统已建立。并行骨架实现的本地模式应满足以下边界：

| 项目 | 当前 demo 约定 | 生产化前不得宣称 |
| --- | --- | --- |
| 登录 | 无凭据、本地会话 | 真实账号、跨设备同步和安全鉴权 |
| 识别 | 默认启发式；可选 OpenAI provider 尚未用真实 key 验收 | 生产准确率与稳定性 |
| 存储 | `localStorage` | PostgreSQL 持久化、备份和恢复 |
| 营养 | fixture/标准模型的本地计算 | 完整中国食物数据和医学级准确性 |
| 照片/语音 | 契约预留或手动回退 | 云端图片理解、语音转录与留存 |

这张表是验收时的事实边界；实现状态以代码、测试和运行日志为准，不能用产品愿景替代验证证据。

## 3. 里程碑与验收

### M0：文档、边界和可运行骨架

**目标：** 任意开发者能安装并启动项目，看到本地 demo 的最小闭环。

- [x] Next.js 移动端友好页面和基础路由；
- [x] 无凭据 demo 登录/退出和本地用户隔离；
- [x] 文字、照片预览和浏览器语音输入；
- [x] 启发式识别器返回和 OpenAI provider 相同的结构化 shape；
- [x] 用户可以查看候选、修改份量/油量并确认；
- [x] 本地 Nutrition Engine 计算 kcal、蛋白质、脂肪、碳水与范围；
- [x] `localStorage` 保存餐食和今日汇总；
- [x] 空状态、识别失败和保存失败有可理解的回退；
- [x] `npm install`、`npm run dev` 运行方法写入 README。

**验收证据：** 浏览器手动完成一餐；刷新后记录仍在；没有配置云凭据时无网络 AI 请求；低置信项目要求确认。

### M1：领域契约与 Nutrition Engine 固化

**目标：** AI 只是可替换的候选生产者，营养计算可以独立测试。

- [x] 以运行时 schema 校验 `MealAnalysisResult`；
- [x] 以独立函数边界实现 OpenAI 与本地启发式 provider；
- [ ] 定义 `food`、`recipe`、`portion profile`、`meal item` 和 `nutrition estimate` 领域类型；
- [x] 份量表达支持半碗、一碗、几块、三分之一盘、一勺、一两、两口；
- [x] 计算结果包含范围、置信度和来源；`engine_version` 待持久化阶段补齐；
- [x] schema 明确拒绝 AI 直接提供的营养真值；
- [ ] 为油量、合菜分摊和个人餐具建立 fixture 测试。

**验收证据：** 单元测试覆盖正常、低置信、未知油量、多人分摊、缺少数据和不合法 schema；更换 analyzer 不改变 engine 测试结果。

### M2：真实数据边界与个人记忆

**目标：** 让中餐场景的高频输入可复用、可审计。

- [ ] 建立可版本化的食物/菜谱数据导入格式；
- [ ] 评估 Open Food Facts、USDA 和中国食物数据的质量、许可与字段差异；
- [ ] 支持系统标准菜谱与用户家庭菜谱；
- [ ] 支持常吃食物、别名、个人餐具和历史份量基准；
- [ ] 保存数据来源、版本、导入时间和计算版本；
- [ ] 过去已保存餐食以快照显示，不被数据更新静默改写。

**验收证据：** 用户创建一道家庭菜后，下一次可以复用；修改菜谱不会改变旧餐食快照；每个营养值可回溯到 food/recipe 数据源。

### M3：Supabase Auth/PostgreSQL 生产骨架

**目标：** 将本地领域对象迁移到真实账号和服务端持久化，同时保留 demo 回退。

- [ ] Supabase Auth 登录、退出、会话过期和错误状态；
- [ ] PostgreSQL 表、迁移和必要的行级权限/服务端所有权检查；
- [ ] 服务端保存 meal、items、inputs、estimates、recipes 和 ai runs；
- [ ] localStorage 与生产存储通过接口隔离，不能在页面中写两套业务逻辑；
- [ ] 照片/音频对象存储、大小/类型校验、删除和留存策略；
- [ ] 导出/删除用户数据的最小路径。

**验收证据：** 两个账号无法互读或互改；刷新和跨设备登录能读取服务端历史；未配置生产环境变量时仍可启动 demo；凭据不出现在浏览器 bundle。

### M4：OpenAI Responses API provider

**目标：** 将真实多模态/自然语言理解接入现有契约，不改变下游计算。

- [ ] 服务端实现 OpenAI Responses API provider；
- [ ] 文本、图片和语音转录分别归一化到统一输入对象；
- [ ] 使用严格结构化输出并做服务端 schema 校验；
- [ ] 设定超时、重试、限流、最大输入大小和成本监控；
- [ ] 记录 provider/model/schema 版本、状态、延迟和必要的成本元数据；
- [ ] provider 错误、超时、无效输出和低置信结果回退到手动路径；
- [ ] 通过 fixture/录制响应测试，避免单元测试依赖实时 API。

**验收证据：** 使用测试 key 完成一餐识别；API 不可用时输入不丢失且可手动保存；AI 替换为本地 provider 后历史与 Nutrition Engine 测试不变。

### M5：真实用户验证与 V1 发布门

**目标：** 用数据验证是否真正减少中餐记录摩擦。

- [ ] 设计首批 20 名目标用户测试，每人至少 10 餐；
- [ ] 记录完成时长、确认修改次数、主要食物召回率、失败原因和 API 成本；
- [ ] 覆盖家常菜、外卖、合菜、火锅/汤面和海外华人常见替代食材；
- [ ] 检查照片/语音同意、删除、导出和隐私文案；
- [ ] 复盘 200 餐后的暂停指标：召回率 < 85% 或修改次数持续 > 2 时，照片识别回退到文本优先；
- [ ] 完成构建、静态检查、单元测试、关键流程浏览器测试和移动端手动验收。

**发布门：** 核心链路可用、失败可回退、身份隔离有效、数据来源可追溯、没有把 AI 输出当作营养真值，并且用户知道结果是估计值。

## 4. 建议的开发顺序

按一条可运行的垂直链路推进：

```text
本地登录
  ↓
输入草稿（先文本，照片/语音遵守同一契约）
  ↓
启发式 analyzer → schema 校验
  ↓
确认页（份量、油量、分摊）
  ↓
fixture food/recipe → Nutrition Engine
  ↓
localStorage → 今日汇总
  ↓
替换存储适配器为 PostgreSQL
  ↓
替换 analyzer 为 OpenAI provider
  ↓
个人菜谱、餐具、合菜和真实数据
```

每一步完成后都应保留前一步的 fallback。不要先做社区、商城、课程、复杂运动同步或独立 AI 教练。

## 5. 验证计划

### 自动化

- 类型检查和 lint：检查 schema、领域类型和边界；
- Nutrition Engine 单元测试：份量归一化、油量范围、分摊、缺少数据；
- provider 契约测试：本地 analyzer 和 OpenAI fixture 都通过同一 schema；
- 存储适配器测试：localStorage 与 PostgreSQL 实现满足同一读写契约；
- API/集成测试：未登录、跨用户访问、AI 失败和保存重试；
- 浏览器测试：登录 → 输入 → 确认 → 保存 → 刷新 → 今日汇总。

### 本地命令占位

```bash
npm install
npm run dev
npm run lint
npm test
npm run build
```

如果某个脚本在当前骨架中尚未定义，应把它列为对应里程碑待办，不得把“命令未找到”描述成测试通过。实时 OpenAI/Supabase 测试需要本地环境变量；默认的单元测试必须不依赖网络或真实凭据。

## 6. 风险登记

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| AI 识别常见中餐仍不稳定 | 主要食物召回率低、确认次数高 | 文本优先、别名/家庭菜谱、扩大 fixture，暂停照片扩张 |
| 营养结果过度精确 | 用户把单值当医学事实 | 展示范围/置信度/原因，Engine 拒绝模型营养真值 |
| 10 秒目标被上传和模型延迟拖慢 | P50/P95 输入到保存超时 | 先保存草稿、并行预处理、超时回退、异步重算（必要时再评估） |
| 数据源许可或质量不足 | 导入字段无法追溯 | 先做来源登记和抽样审核，再扩大数据 |
| 云接入扩大安全边界 | 凭据进入客户端、跨用户读写 | 所有 provider/service role 仅服务端；会话与所有权检查；安全测试 |
| 范围膨胀 | 出现社区/商城/课程/复杂运动任务 | 回到 V1 核心链路，新增需求先写验收和成本 |

## 7. 决策记录

- **选择 Next.js 单体 PWA：** 优先移动端体验和一条端到端链路，降低部署复杂度；
- **选择可替换 AI provider：** OpenAI 只是当前默认实现，用户数据和营养计算不绑定任何模型；
- **选择本系统 Nutrition Engine：** 让营养结果可追溯、可测试、可修正；
- **选择 local demo：** 没有云凭据也能验证交互和数据模型，但不伪称生产能力；
- **暂不选择微服务/Kubernetes/向量库：** 当前未知数是产品/数据质量，不是规模基础设施。
