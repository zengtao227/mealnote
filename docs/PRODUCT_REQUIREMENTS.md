# MealNote 产品需求文档（PRD）

**版本：** V1.0 草案  
**产品状态：** 本地 demo 骨架 → 生产化迭代  
**最后更新：** 2026-08-25

## 1. 产品定义

MealNote 是面向中国饮食习惯和海外华人的极简 AI 饮食记录器。它把“记录我吃了什么”从逐项搜索、称重和手填克数，改成拍照、语音或自然语言输入，再由用户做极少量确认。

产品价值不是给出看似精确的单一数字，而是：

- 理解中餐合菜、家常菜、外卖和多人共享的真实场景；
- 把“半碗、几块、三分之一盘、两口”等自然份量转成可计算的估计；
- 把油量、菜谱差异和分摊比例等最大误差来源展示给用户；
- 让用户在约 10 秒内完成一餐记录，并能随时纠正和复用自己的数据。

MealNote 不做综合减肥平台。社区、商城、课程、复杂运动同步和全天候 AI 教练不属于 V1。

## 2. 用户与问题

### 目标用户

1. 在中国生活、经常吃家常菜和外卖的饮食记录用户；
2. 在海外生活、仍以中餐为主要饮食的华人；
3. 想建立个人饮食观察习惯，但不愿意为每道菜称重或查数据库的用户。

### 核心痛点

传统热量应用通常假设用户吃的是包装食品或单一食物，要求逐项搜索、选择克数。对番茄炒蛋、红烧排骨、火锅、汤面、家庭合菜而言，用户很难准确回答“我吃了多少克”和“用了多少油”。

固定词典可以计算已确认数据，却无法独立理解自由文本、语音、照片、份量词和合菜分摊关系；让 AI 直接输出营养真值又不可审计、不可稳定复现。因此产品必须拆开“理解”与“计算”。

## 3. 目标与衡量

### 产品目标

- 用户在一部手机上完成登录、输入、确认、保存和今日汇总；
- 典型一餐从开始输入到保存的中位时间不超过 10 秒；
- 识别失败或低置信时，用户能在同一页面手动完成记录；
- 估计结果包含范围、置信度和不确定性来源，避免制造虚假的精确感；
- 用户确认过的食物、菜谱、餐具和份量基准可以在下一餐复用。

### 首轮质量基线

这些是需要通过真实用户测试验证的目标，不是当前 demo 已经证明的事实：

| 指标 | V1 目标 | 测量方式 |
| --- | --- | --- |
| 完成一餐的中位时长 | ≤ 10 秒 | 首批 20 名目标用户，每人至少 10 餐 |
| 确认页修改次数中位数 | ≤ 2 次 | 记录 AI 候选到最终确认的编辑次数 |
| 主要食物召回率 | ≥ 85% | 累计至少 200 餐，对照用户最终确认结果 |
| 低置信项提示覆盖率 | 100% | 任何低于阈值的候选必须显式要求确认 |
| AI 不可用时的完成率 | 可完成 | 使用常吃食物、菜谱或手动份量回退 |

若 200 餐后主要食物召回率仍低于 85%，或大多数餐食需要超过 2 次修改，应暂停扩大照片识别，回退到文本优先和更强的手动确认。

## 4. V1 范围

### 4.1 核心链路（P0）

```text
登录 → 拍照/文字/语音输入 → 结构化识别
    → 快速确认/修改 → Nutrition Engine 计算
    → 保存 → 今日汇总
```

#### 登录

- 本地 demo：提供无凭据的本地 demo 登录，只用于在浏览器内隔离当前用户数据；
- 生产：使用 Supabase Auth，用户身份和数据访问由后端会话控制；
- 未登录用户不能读取或修改另一个用户的餐食历史。

#### 输入

- 文本：支持“午饭半碗米饭，番茄炒蛋三分之一盘，排骨四块”；
- 照片：支持餐前/餐后照片，保留照片与识别结果的关联；
- 语音：把自然语音转为可追溯的文本，再进入相同的结构化识别流程；
- 多种输入可以合并，例如照片 + “我只吃了左边一半”；
- 输入原文必须保留，便于回看、重试和纠错。

本地 demo 默认使用启发式识别和浏览器 `localStorage`；配置服务端 `OPENAI_API_KEY` 后可以切换到 OpenAI provider，但真实模型质量尚未验收。无 key 时照片只作预览，识别来自文字；语音依赖浏览器转文字能力。

#### 结构化识别

AI 只负责：

- 判断食物/菜名、类型和可能的食材；
- 解析份量表达并估计克数范围；
- 估计油量等级或标记未知；
- 判断合菜分摊、餐前/餐后差异和需要用户回答的问题；
- 对每个候选给出置信度和确认建议。

AI 不负责：

- 直接决定最终 kcal、蛋白质、脂肪和碳水；
- 把模型训练记忆当作本系统的食物库或用户历史；
- 在低置信度时静默写入已确认数据。

严格输出契约见 [架构说明](ARCHITECTURE.md#6-ai-结构化输出契约)。

#### 快速确认与修改

- 用户可以逐项修改食物名、份量、分摊比例和油量；
- 低置信度项目必须有明显的“请确认”状态；
- 常见份量以中文表达优先，允许用户直接选“半碗、1 碗、4 块、1 勺、两口”等；
- 用户不需要为了保存餐食而理解数据库 ID 或克数；克数属于可展开的估计细节；
- 用户确认值覆盖 AI 候选，并记录来源为 `user`，不可被下一次识别静默覆盖。

#### Nutrition Engine

Nutrition Engine 根据以下顺序计算营养结果：

1. 用户最终确认的食物/菜谱和份量；
2. 本系统可信的食物数据、标准菜谱模型和品牌食品数据；
3. 用户自定义菜谱、家庭菜谱、个人餐具体积和历史确认过的份量基准；
4. 对油量、食材比例、分摊比例等不确定因素生成合理范围与置信度。

输出至少包括 kcal、蛋白质、脂肪、碳水、估计范围、引发范围的变量和计算版本。无数据时应返回“需要补充/手动选择”，而不是让 AI 填一个看似精确的数字。

#### 保存与今日汇总

- 保存完整餐食、输入、候选、用户确认值和 Nutrition Engine 结果；
- 今日汇总按餐食累加四大营养素，同时保留每餐范围；
- 可查看原始输入和修改记录；
- 本地 demo 写入当前浏览器 `localStorage`；生产目标写入 Supabase PostgreSQL。

### 4.2 中国饮食场景能力（P1，按垂直切片渐进交付）

以下能力是产品方向的一部分。第一条完整闭环先以最小数据模型承载，再逐步提高 UI 和数据质量：

| 场景 | 需求 |
| --- | --- |
| 份量表达 | 半碗、一碗、几块、三分之一盘、一勺、一两、两口等可解析、可确认、可复用 |
| 合菜分摊 | 记录整盘菜、总人数/个人比例或“我吃了约三分之一”，避免把整盘营养算给一个人 |
| 家庭菜学习 | 用户确认后可保存为个人/家庭菜谱，记录配料、烹饪方式和油量假设 |
| 餐前/餐后照片 | 支持照片对比，辅助估算剩余比例；照片仍需用户确认，不能假定像素等于克数 |
| 油量确认 | 低/中/高/未知或直接估计用油，突出油量带来的范围变化 |
| 常吃食物 | 用户确认过的条目可快速复用，作为 AI 失败时的回退 |
| 个人餐具记忆 | 用户可把自己的碗、勺、盘定义为份量基准，不将其当成通用标准 |

### 4.3 成功与失败回退

- AI 返回可用候选：展示候选，用户快速确认后计算；
- AI 返回低置信候选：突出需要确认的项目和不确定性来源；
- AI 超时/额度不足/不可用：保留原始输入，切换到常吃食物、标准菜谱或手动添加；
- Nutrition Engine 缺少可信数据：允许用户选择近似食物或录入菜谱，标记结果为低置信；
- 保存失败：不丢失已输入内容，提示重试或导出/复制（生产需有更明确的离线策略）。

## 5. 非目标（V1 不做）

- 社区、动态、点赞、社交排名；
- 商品商城、广告导购和营养品销售；
- 付费减肥课程、问诊和医疗诊断；
- 复杂运动设备同步、训练计划和运动处方；
- 独立的全自动 AI 教练或主动任务分发；
- 追求“拍照后无确认、精确到个位数 kcal”的营销承诺；
- 为了预想中的规模引入微服务、Kubernetes、向量数据库或复杂事件总线。

## 6. 关键用户故事与验收标准

### US-01：10 秒记录一餐

作为一个吃中餐的用户，我想说一句“午饭半碗米饭、排骨四块”，这样不用搜索和称重也能留下可用记录。

**验收：** 输入原文被保存；候选包含食物名、中文份量、克数估计、油量、置信度；用户可以在确认页内完成保存；低置信项目不会被静默确认。

### US-02：修正合菜和分摊

作为和家人一起吃饭的用户，我想记录“整盘番茄炒蛋，自己吃了三分之一”，这样今日汇总不会计算整盘。

**验收：** 数据模型能区分菜品总量与个人分摊量；最终计算只使用个人份量；原始估计和用户修正都可追溯。

### US-03：理解不确定性

作为关注饮食趋势而非小数点精度的用户，我想知道结果为什么是一个范围。

**验收：** 结果展示单值近似值、合理范围、置信度和最大不确定因素（例如油量或分摊比例）；模型无法确定时展示未知或需要确认。

### US-04：复用个人菜谱与餐具

作为经常吃同一道家常菜的用户，我想保存自己的菜谱和碗的容量，以便下次少确认一步。

**验收：** 用户数据持久化在本系统；下一次可搜索/选择复用；修改菜谱时已有餐食的历史快照不被无意重算。

### US-05：AI 不可用仍能记录

作为网络不稳定或不愿授权云端的用户，我想手动完成一餐。

**验收：** 原始输入不丢失；可以从常吃食物、标准菜谱或手动份量添加项目；结果标注数据来源和较低置信度，而不是报错后无法使用。

## 7. 数据与信任原则

- 用户历史、菜谱、份量基准和营养结果属于 MealNote 系统；模型更换不得改变历史记录的审计内容；
- AI 输出只能作为待确认候选，不能越过确认直接成为营养真值；
- 任何外部食物数据都要记录来源、版本、许可和导入时间；
- 照片、语音和原始文本属于用户输入，生产接入前必须明确用途、保留期、删除和导出机制；
- 产品提供估计和记录工具，不提供医疗诊断、治疗建议或个体化医学结论。

## 8. 约束、风险与开放问题

### 已知风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 混合菜和油量难以从照片判断 | 营养范围过宽或误导 | 让用户确认油量/份量，展示范围，不输出伪精确值 |
| 中文菜名地域差异 | 食物匹配错误 | 保存原文和候选，允许用户改名，建立别名/用户菜谱 |
| 合菜分摊不清 | 热量被整盘计算 | 单独建模总量、个人比例和人数 |
| 外部数据许可或质量不稳定 | 数据不可用/不可商用 | 记录来源与版本，优先自有可审计模型 |
| AI API 成本、延迟和不可用 | 10 秒目标被破坏 | provider 超时、缓存、文本回退和本地启发式识别 |
| 用户隐私和照片泄露 | 信任与合规风险 | 最小化留存、明确同意、后端鉴权、删除/导出机制 |

### 需要后续确认

- 中国食物数据的首批可信来源、许可范围和审核方式；
- 照片/语音默认留存还是仅保留解析结果；
- 目标市场的登录方式、地区合规和付费模型；
- 个人餐具体积的初始录入体验；
- 置信度阈值和范围生成方式应由 200 餐数据校准，而不是凭感觉固定。
