# 提案：S3.5 — 食物解析可用性与「10 秒记录」验证

> **状态：未批准（PROPOSAL）。** 本文件是待独立复审的提案，不是已批准的开发计划。
> 在复审 APPROVE 之前，不得据此实施任何代码，也不得改变 `docs/DEVELOPMENT_PLAN.md` 第 4 节的既定顺序（当前下一优先项是 S4）。
>
> **提出时间：** 2026-08-27，S3（PR #7）合并后
> **主张的位置：** S3 之后、S4 Auth 之前


## 0. 为什么插在 S4 之前

S4/S5 把关的是**能不能上线**（身份、成本、真实 key）。S3.5 把关的是**值不值得上线**——「10 秒记录一餐」是 PRD 的核心承诺，也是 `DEVELOPMENT_PLAN.md` 交付原则第 1 条，但 S0→S3 没有任何一步触及它。

S3.5 不需要 Auth、不需要云、不需要 API key，可完全离线推进，因此它没有理由排在 S4 之后。若验证结果证伪核心前提，产品形态本身要改，此时再补 Auth 与成本保护会返工。

## 1. 一个必须先说清楚的耦合

**扩 catalog 会放大 S2 处理的那类风险，而不是取代它。**

当前 7 条 profile 的别名碰撞面极小。一旦引入 `面条 / 汤面 / 牛肉面`、`米饭 / 蛋炒饭 / 糯米饭`、`饺子 / 蒸饺 / 煎饺` 这类同族条目，substring 提升、broad/compound 抑制、重复 mention 绑定的组合数量会随条目数超线性增长。

因此：

- **不弱化、不删除**现有 mention-span / authority / confirmation / stale-response 测试；S3.5 会让它们承受更大压力，是它们真正的第一次负载检验；
- 每次扩 catalog 都必须先跑 **别名碰撞审计**（见 A3），审计不通过不得合入新条目；
- `silent wrong canonicalization rate` 是本阶段的**阻断性指标**，不是观察指标。

## 2. A — 语料与指标

### A1. 语料构建

建立 `fixtures/meal-corpus/`，全部为合成或公开来源的中式饮食输入，**不含任何个人隐私数据**。每条带 ground truth 标注：

```jsonc
{
  "id": "corpus-0001",
  "input_text": "午饭半碗米饭，三分之一盘番茄炒蛋",
  "source": "text",
  "expected_items": [
    { "identity": "米饭",   "span": [4, 7],  "expected_grams_range": [90, 110] },
    { "identity": "番茄炒蛋", "span": [9, 17], "expected_grams_range": [100, 140] }
  ]
}
```

覆盖面（按 PRD 第 4 节和 M5 验收面）：家常炒菜、主食、外卖、合菜分摊、火锅/汤面、海外华人替代食材、口语份量（半碗/几块/三分之一盘/一勺/一两/两口）、多子句与未枚举连接词、复合菜名。

规模由覆盖面驱动，先做到每类 ≥ 10 条即可开始度量，不预设总数。

### A2. 指标——区分「可离线测」与「必须真人测」

这是必须先讲清的一点：用户列出的 6 个指标里，只有前 4 个能在 S3.5 离线得到，后 2 个需要真人。

**可离线测（S3.5 内闭环）：**

| 指标 | 定义 | 门槛 |
| --- | --- | --- |
| catalog resolution rate | ground truth item 中被 exact resolver 正确解析的比例 | 由 A4 基线决定，不预设 |
| unresolved item rate | 走到 `NutritionResolutionError` 的 item 比例 | 同上 |
| **silent wrong canonicalization rate** | 解析出的 canonical ≠ ground truth identity **且** 该 item 未被标 `needs_confirmation` 的比例 | **必须 = 0，阻断性** |
| required edits per meal | 从 provider 候选到可保存状态所需的最小 UI 编辑次数（脚本可判定） | 中位 ≤ 2 |

**必须真人测（不在 S3.5，留给 M5）：**

| 指标 | 为什么不能离线 |
| --- | --- |
| 输入→保存 median / P90 时长 | 脚本时长不是人的时长；离线数字会制造虚假达标感 |
| 完成保存比例 | 放弃行为只有真人会产生 |

S3.5 对这两项的替代物是上表的 `required edits per meal`（交互次数代理量），并明确标注为**代理指标，不等于 10 秒达标**。真正的 10 秒结论只能在 M5 下判定。

### A3. 别名碰撞审计

对任意 catalog 变更，自动检查并在 CI 失败：

- 任一 profile 的 canonical/alias 是否为另一 profile 的 canonical/alias 的子串；
- 命中时必须存在对应的 mention-span 回归用例覆盖两个方向的顺序与未枚举连接词；
- 无覆盖则拒绝合入。

### A4. 基线测量（先测后改）

**在扩任何 catalog 之前**，用当前 7 条 profile 跑一遍全语料，产出 miss 分布报告：按食物族、按份量语法、按输入结构分类统计 unresolved 与 wrong-canonicalization。

**首批 catalog 范围由这份报告的实际 miss 分布决定，不设「扩到 200 条」这类武断目标。**

## 3. B — 给 fail-closed 提供出口

当前确认页 `food_name` 只有自由文本框（`meal-workbench.tsx:692`），未匹配时用户看到「请修改为明确的食物或菜谱名称」却无从知道合法条目，是死路。

最小改动：

- catalog 搜索（前缀 + 别名匹配，纯内存，数据源就是 `FOOD_PROFILES`）；
- 输入时给支持项建议；
- 展示 canonical name 与命中的 alias（让用户看懂"你选的是哪一条"）；
- 未匹配时明确列出当前可选条目，而不是只报错；
- 用户手工修改后**仍由 exact resolver 重新验证**——选择器是输入辅助，不是 authority 旁路。

**不引入** Dexie、状态框架、后台索引服务。

## 4. C — item-level 原始证据

### 问题

整餐 `input_text` 已保存，但 `item.food_name` 是 provider 处理后的名称。`糯米饭` 场景下 UI 显示「米饭 → 米饭」，用户原话里的 `糯` 在上游就丢了，错配不可见。

### 最小 schema

给 item 增加**可选**字段：

```ts
source_evidence?:
  | { kind: "text-span"; start: number; end: number; quoted_text: string; verified: boolean }
  | { kind: "none" }
```

规则：

- **heuristic**：直接使用它已有的真实 mention span（`heuristic-provider.ts` 内部已按 span 建候选，属于暴露既有信息，不新增解析逻辑）；
- **文本 OpenAI**：模型返回 quoted source，**服务端必须校验** `input.text.slice(start, end) === quoted_text`；
- **校验失败**（模型编造证据）：降级为 `kind: "none"` **并强制该 item `needs_confirmation = true`**，而不是拒绝整份分析——拒绝整份会让不稳定的 provider 变成可用性故障；
- **图片-only item**：允许 `kind: "none"`，不因此惩罚；
- 三层展示分离：**用户原话 / 可验证文本片段** → **provider candidate** → **最终 catalog match**；
- provider candidate 仍然不是 nutrition authority，本字段不改变这一点。

### 一个必须避免的过度宣称

`/api/analyze` 的服务端校验只能证明「该文本片段确实存在于本次请求的原始输入」。`/api/nutrition/calculate` 仍然独立接收客户端提交的 items，**没有服务端原始 analysis 绑定**。

所以：S3.5 之后，evidence 在 analyze 出口是 server-verified，在 calculate 入口仍是 client-reported。**不得**因为本阶段就把 calculate 侧的 provenance 标记升级为已验证。真正的升级仍要等 S2 推迟的服务端 analysis binding。

## 5. D — OpenAI provider 契约测试

`openai-provider.ts`（89 行）当前 0 测试，而它是配置真实 key 后的主路径。

**不**强制模型从 catalog enum 里选：未知食物会被迫错映射到最近的合法条目，等于用 schema 制造 silent wrong canonicalization——正是阻断性指标要杜绝的。

正确形态：

- 允许 unknown / unresolved candidate（`food_name` 保持自由文本）；
- 可在 prompt 中提供 catalog shortlist，或让模型返回**可选的** `suggested_catalog_id`；
- 建议值**必须由服务端 resolver 重新验证**，验证不过即丢弃建议，不影响 item 本身；
- JSON schema 继续禁止 kcal / 蛋白质 / 脂肪 / 碳水等营养真值字段；
- 用 mock / recorded fixtures 覆盖：

  1. 正常支持食物
  2. 未知食物（必须走 unresolved，不得被强行映射）
  3. compound：`糯米饭` / `蛋炒米饭`
  4. 模型错误建议 canonical（建议必须被服务端驳回）
  5. schema violation（strict 拒绝）
  6. timeout / API error / heuristic fallback 路径
  7. 原始文本证据不匹配（降级为 `none` + 强制 confirmation）

## 6. E — CI

S3 merge 后**单独**开一个小型 release-engineering PR，只含一个可复用的 Node 22 workflow：`npm ci` / lint / typecheck / test / build / `npm audit`。

不再为任何 PR 创建 `s3-final-verify-vN` 这类一次性 workflow。

## 7. 拆分顺序与门

```
PR #7 (S3) 独立 APPROVE + merge
        ↓
E   CI PR（最小、独立、先落地，后续所有 PR 复用）
        ↓
A1  语料 + ground truth 标注               ← 无生产代码变更
        ↓
A4  7 条 profile 基线测量 + miss 分布报告   ← 决策输入，不改代码
        ↓
   ┌────┴─────────────────────────┐
   │  门：silent wrong canonicalization 基线是否为 0？  │
   │  非 0 → 先修 authority，不得扩 catalog             │
   └────┬─────────────────────────┘
        ↓
B   catalog 搜索/建议 UI（fail-closed 出口）  ← 今天唯一的硬墙，尽早拆
        ↓
C   source_evidence schema + 服务端校验 + 三层展示（落到 B 建好的界面里）
        ↓
D   OpenAI provider 契约测试（7 类 fixture，含 C 的证据不匹配用例）
        ↓
A3  别名碰撞审计常驻 CI                     ← 必须早于任何 catalog 变更
        ↓
A2  按 miss 分布扩 catalog（每批都过 A3 审计 + 重测指标）
        ↓
   门：required edits 中位 ≤ 2 且 silent wrong = 0
        ↓
S4  Supabase Auth + session-derived owner
```

顺序理由：

- **E 最先**，因为后面每一步都要复用它，且它与业务代码零耦合；
- **A1/A4 先于任何代码改动**，避免「先扩 catalog 再找理由」的确认偏误；
- **B 尽早**，因为它是 S3.5 里唯一移除当前硬性用户死路的动作（未匹配时无从知道合法条目）。
  > **修正：** 本方案早先版本把 C 排在 B 之前，理由是「搜索 UI 要展示用户原话 → catalog match，缺 evidence 就只能展示 provider 处理后的名称」。核对后该依赖**不成立**：`engine.ts:139` 调用的是 `resolveFoodProfile(item.food_name)`，只接受字符串；B 只需要 `FOOD_PROFILES` 与 `resolveFoodProfile`，与 `source_evidence` 无关。三层展示是 C 的交付物，B 建好的界面后续承载它即可。B 独立可发，且严格优于现状，因此提前。
  >
  > B 单独上线时的唯一约束：**不得把 provider 处理后的名称呈现为「你说的话」**。在 C 落地前，该位置只显示 provider candidate 与 catalog match 两层，缺的第三层留空而不是用 candidate 冒充。
- **C 在 B 之后**，把 evidence 层加进已有界面，避免为不存在的依赖拖延 B；
- **D 在 C 之后**，因为 D 的 fixture 第 7 类（原始文本证据不匹配）需要 C 的服务端校验语义先定下来；
- **A3 必须早于 A2**，审计不存在时不得合入任何新 catalog 条目；
- **A2 扩 catalog 放最后**，因为它是唯一会放大 authority 风险的动作，必须在证据、审计和测试都就位后进行。

## 8. 明确非目标

- 不引入 Dexie、Redux/Zustand 等状态框架、后台索引服务；
- 不做 Supabase Auth、真实 OpenAI key 部署、per-user rate limit（属 S4/S5）；
- 不做数据库 schema 重设计；
- 不弱化或删除任何现有 S2 测试；
- 不在本阶段声称「10 秒达标」——该结论只能由 M5 真人数据给出。
